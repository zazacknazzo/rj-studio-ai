# V0.1 — Pre-V1 foundation hardening

Status: complete
Implementation approval: granted on 2026-09-13
Completed: 2026-09-13; real Sandbox acceptance tested on commit `0e3071f`

## Problem statement

V0 proves the local Twilio webhook flow, but its failure semantics are not safe enough for a non-deterministic or costly reply generator. A callback can be recorded before its reply is returned, concurrent retries are untested, provider-specific form parsing leaks into the HTTP route, schema changes are not versioned, imports create a database, liveness can hide an unusable configuration, and Message retention is undefined.

V0.1 makes this foundation predictable without adding AI, CRM, SaaS, or new customer-facing behavior.

## Scope

V0.1 delivers five small vertical slices:

1. **Recoverable webhook processing:** one logical response is created and stored for each provider Message, and every retry replays that same non-empty response.
2. **Provider-neutral HTTP intake:** the route passes an unparsed request envelope to the configured WhatsApp Provider; Twilio owns form parsing, signature validation, and TwiML.
3. **Explicit database lifecycle:** Alembic revisions upgrade fresh and existing V0 databases, and importing modules performs no filesystem or database initialization.
4. **Operational readiness and data lifecycle:** liveness stays compatible, readiness reflects usable configuration and persistence, and a minimal retention/deletion policy is enforced.
5. **Real Sandbox acceptance:** a repeatable Twilio Sandbox smoke test is run and its evidence is recorded without secrets or real Message content.

## Behavioral contract

### Retry and concurrency semantics

- The idempotency key remains the provider plus its stable Message identifier. For Twilio inbound Messages, this is `MessageSid`.
- The first valid attempt atomically stores the inbound Message and the exact logical Automatic Reply selected for it.
- A later or concurrent attempt for the same idempotency key returns the stored reply. It must not use changed configuration, create another outbound row, or return an empty acknowledgement.
- Only one inbound row and one logical outbound row may exist for that provider Message.
- Duplicate attempts must not advance Conversation activity timestamps.
- A failure while constructing the provider response must leave enough durable state for the next attempt to return the same reply.
- V0.1 guarantees exactly-once reply generation and persistence plus deterministic response replay. It does not claim exactly-once delivery by Twilio or WhatsApp; delivery confirmation requires provider status callbacks and is outside this version.
- Twilio retry headers may be recorded as redacted diagnostics, but they are not the domain idempotency key.

### Provider seam

- `POST /webhooks/twilio` is the canonical Twilio route. `POST /webhooks/whatsapp` remains as a V0-compatible alias with the same successful response contract.
- The route captures method, exact public URL, headers, query data, content type, and raw body without interpreting Twilio form fields.
- `WhatsAppProvider` receives that request envelope and owns provider-specific authentication, parsing, validation, and response construction.
- `TwilioProvider` continues using the supported Twilio validator and must accept evolving Twilio parameter sets.
- Missing fields, unsupported content types, and malformed form bodies become provider payload errors mapped to HTTP 400.
- Invalid Twilio signatures remain HTTP 403 and must cause no persistence.
- Missing required provider configuration is an availability failure, not an invalid-caller response.

### Database lifecycle and migrations

- Alembic applies ordered, versioned migrations and records the current revision in the database.
- A fresh database reaches the current schema through migrations only.
- An existing V0 database upgrades without losing Conversations or Messages.
- Each migration is atomic. A failed migration is not recorded as applied and readiness remains unavailable.
- The migration that supports retry replay preserves the relationship between one inbound Message and its prepared outbound reply.
- Importing `rj_studio_ai.main`, `create_app`, or persistence modules must not create directories, files, tables, or rows.
- Database initialization and migrations run through explicit application lifecycle or an explicit migration command.

### Liveness and readiness

- Existing `GET /health` behavior remains the liveness contract for V0 compatibility.
- New `GET /ready` returns HTTP 200 only when migrations are current, SQLite can begin a write transaction, the Automatic Reply is non-empty, and required Twilio credentials are present when signature validation is enabled.
- `GET /ready` returns HTTP 503 with safe, machine-readable check names when a requirement fails. It never returns secret values.
- Readiness does not call Twilio or WhatsApp over the network.
- A failed readiness check must not leave test rows or other durable changes.

### Initial Message retention and deletion policy

- Raw inbound and outbound Message rows are retained for 90 days by default, configurable through `MESSAGE_RETENTION_DAYS`.
- Expired Message rows are deleted only through an explicit maintenance command; V0.1 adds no startup purge, scheduler, or background worker.
- Conversations with no remaining Messages are deleted.
- An operator can delete one Conversation and its Messages by provider and customer address through a documented local maintenance command. No public deletion endpoint is added.
- Purge and deletion operations are transactional, idempotent, and report counts without logging customer addresses or Message bodies.
- Tests use a fixed clock and synthetic data.
- This is an initial product policy, not a claim of legal or regulatory compliance. The approved default is 90 days.

### Real Twilio Sandbox smoke test

- Add one concise runbook under `docs/runbooks/` covering prerequisites, startup, HTTPS tunnel, Sandbox webhook configuration, signature validation, test Message, database verification, and cleanup.
- Run the smoke test with signature validation enabled and a fresh database.
- Verify that a joined WhatsApp account sends one unique synthetic Message, receives the configured Automatic Reply, the webhook returns HTTP 200, and the database contains one inbound plus one outbound record.
- Record date and timezone, commit SHA, result, exact steps executed, expected versus observed behavior, and redacted evidence in the runbook.
- Never record the Auth Token, full phone number, tunnel credential, real customer content, or unredacted identifiers.
- V0.1 cannot move to `complete` until this real smoke test has a recorded passing result.

## Acceptance criteria

1. A valid first callback returns the configured non-empty TwiML reply and stores one inbound/outbound pair.
2. Sequential retries return the original stored reply, even when the configured Automatic Reply has changed since the first attempt.
3. Concurrent callbacks for the same `MessageSid` all complete without SQLite lock errors, return the same non-empty reply, and leave exactly one inbound/outbound pair.
4. A simulated failure after reply persistence is recoverable: the next attempt returns the stored reply without generating or storing another one.
5. Duplicate callbacks do not change `conversations.updated_at`.
6. The HTTP route contains no Twilio form-field parsing or Twilio-specific URL setting access.
7. The Twilio adapter accepts the raw request envelope, validates the exact configured public URL, and parses the form body.
8. Invalid signatures return 403; malformed or incomplete payloads return 400; neither path writes Conversation data.
9. Temporary database failures return a retryable 5xx response and never return success TwiML.
10. Fresh-database and V0-to-V0.1 migration tests pass without destructive schema recreation.
11. Re-running migrations is a no-op, and an interrupted migration is not marked complete.
12. Import-isolation tests prove that imports create no database file or directory.
13. `/health` keeps its V0 status and body; `/ready` returns 200 for a usable instance and 503 for invalid provider configuration, unapplied migrations, or an unwritable database.
14. Retention purges only Messages older than the configured cutoff, removes empty Conversations, and is safe to repeat.
15. Explicit Conversation deletion removes the selected synthetic Conversation only and emits no sensitive values.
16. The documented real Sandbox smoke test passes and records its date, commit, steps, result, and redacted evidence.
17. Existing V0 behavior tests remain green, and the complete suite, Ruff, and Python compilation pass.
18. No V1, CRM, SaaS, multi-tenant, Meta Cloud API, scheduling, or advertising behavior is introduced.

## Test seams

- **FastAPI HTTP seam:** webhook success, sequential and concurrent retry behavior, signature and payload failures, liveness, and readiness.
- **Database lifecycle seam:** fresh migration, V0 upgrade fixture, migration rollback, retention cutoff, and explicit deletion.
- **Real provider seam:** one manual Twilio Sandbox smoke run with redacted durable evidence.

Tests assert observable responses and persisted outcomes. They may substitute the true external Twilio network, but must not mock internal application modules.

## Risks

- HTTP callbacks cannot provide a true distributed exactly-once delivery guarantee. The implementation must state its narrower guarantee clearly and never confuse a prepared reply with confirmed WhatsApp delivery.
- Migrating an existing SQLite database can damage history if the upgrade is not exercised against a V0 fixture.
- SQLite concurrency tests can become timing-dependent; synchronize the test start and assert durable outcomes instead of sleeps.
- The explicit retention purge deletes data irreversibly. Its approved 90-day cutoff is fixed in tests, and no purge runs during normal application flow.
- Readiness that is too strict can block local development; checks must reflect required runtime capability and avoid external network calls.
- The real smoke test depends on a Twilio testing environment, an HTTPS tunnel, and a joined WhatsApp account. Missing access blocks V0.1 completion but must not weaken or fake the acceptance result.

## Explicitly out of scope

- LLM calls, prompts, personality, Intent detection, Salon Knowledge retrieval, hallucination protection, or any other V1 behavior
- Customer profiles, memory summaries, Lead scoring, Next Best Action, or CRM behavior
- Meta Cloud API implementation
- Tenant tables, `tenant_id`, multi-business configuration, SaaS onboarding, or generic integration frameworks
- Production deployment, queues, distributed locks, Redis, background workers, or replacing SQLite
- Exactly-once delivery confirmation, Twilio status callbacks, proactive outbound messaging, or fallback webhook infrastructure
- A public data-administration interface, full privacy/compliance program, encryption project, or backup system
- Refactoring unrelated V0 code or changing the customer-visible Automatic Reply

## Source constraints

- Twilio may retry webhooks on configured connection/read failures and exposes `I-Twilio-Idempotency-Token` to distinguish attempts.
- Twilio signature validation requires the exact URL and all request parameters; JSON callbacks require the raw body path supported by its SDK.
- Incoming Messaging webhooks return TwiML; empty TwiML acknowledges without sending a Message.
- The WhatsApp Sandbox is for testing and discovery, and its inbound Message flow calls the configured webhook.
