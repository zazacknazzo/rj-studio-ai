# V1 — AI attendant

Status: draft

## Problem statement

V0.1 recebe uma Message do WhatsApp, persiste a Conversation com segurança e devolve uma Automatic Reply fixa. RJ Studio precisa agora de Lívia, uma AI Attendant que converse em português brasileiro de forma natural, factual e segura.

A V1 precisa impedir respostas inventadas, perda de Messages, geração LLM duplicada, continuidade indevida após Human Handoff e crescimento desnecessário de infraestrutura. Ela continua atendendo somente o RJ Studio e preserva o fluxo existente do Twilio.

## Solution

Estender o fluxo canônico de WhatsApp com um provider LLM estreito, Salon Knowledge aprovada, Conversation Context limitado, decisão estruturada e Human Handoff durável. Fora de Human Handoff ativo, uma inbound Message aceita pode produzir no máximo uma AI Reply curta e customer-visible quando fatos e política permitem. O acknowledgement HTTP do provider não é uma outbound Message de domínio.

A entrega é composta por sete vertical slices. Cada slice mantém o webhook funcional, tem comportamento observável e protege limites críticos com testes. Evals passam a ser parte obrigatória da conclusão da V1.

## User stories

1. As a Customer, I want Lívia to respond naturally in Brazilian Portuguese, so that RJ Studio feels attentive on WhatsApp.
2. As a Customer, I want retries of my Message to replay the same AI Reply, so that I do not receive duplicate or inconsistent answers.
3. As a Customer, I want Messages in the same Conversation handled in order, so that later replies can use earlier results.
4. As a Customer, I want Lívia to ask or hand off when a salon fact is unknown, so that she does not guess.
5. As a Customer, I want Lívia to be transparent when I ask whether she is an AI Attendant, so that I am not misled.
6. As a Customer, I want short WhatsApp responses, so that the Conversation is easy to follow.
7. As a Customer, I want multiple purposes in one Message understood, so that I do not need to repeat myself.
8. As a Customer, I want Lívia to use recent relevant Conversation context, so that natural references work.
9. As a Customer, I want irrelevant or excess history excluded, so that stale details do not influence the reply.
10. As a Customer, I want prices, Services, policies, and Professionals stated only when approved, so that salon facts are trustworthy.
11. As a Customer, I want no promise of availability before V4, so that an Appointment is not falsely confirmed.
12. As a Customer, I want a person to take over sensitive cases, so that RJ Studio can assume responsibility.
13. As a Customer interested in an Appointment, I want Lívia to collect the basics before handoff, so that the team can continue efficiently.
14. As the RJ Studio operator, I want only approved Salon Knowledge published, so that drafts never become customer-facing facts.
15. As the RJ Studio operator, I want operational/commercial and technical facts separated, so that proper validation is visible.
16. As the RJ Studio operator, I want Human Handoff state and reason persisted, so that automation stops reliably.
17. As the project owner, I want model, latency, token, and estimated-cost records without Message bodies, so that V1 can improve without unnecessary PII logging.
18. As the project owner, I want Claude Sonnet 5 and GPT-5.6 Terra compared under equivalent conditions, so that model choice follows evidence.
19. As Joelma, I want the applicable technical cases evaluated against approved guidance, so that her specialties remain safe.
20. As Rogério, I want mega hair cases evaluated against approved guidance, so that related advice remains safe.
21. As a developer, I want durable generation claims, so that in-memory state is not required after restart.
22. As a developer, I want safe LLM failure behavior, so that timeouts and malformed results never produce invented answers.
23. As a developer, I want V1.1 to function without Salon Knowledge, so that costly generation safety is proven before factual answers.
24. As a developer, I want a narrow LLM provider seam, so that a qualified challenger can be evaluated without rewriting the core.
25. As a reviewer, I want eval reports with case and run counts, so that quality percentages are auditable.
26. As a reviewer, I want critical factual and handoff failures visible, so that no prohibited claim is hidden by an average.
27. As an operator, I want to list and release Human Handoffs manually, so that a person controls when automation resumes.
28. As the product owner, I want V1 scope kept separate from CRM, scheduling, and SaaS, so that the foundation remains small.

## Vertical slices

### V1.1 — Safe LLM generation foundation

**Scope**

- Add a narrow LLM provider seam. Claude Sonnet 5 is the production provider; GPT-5.6 Terra is usable only by eval runs.
- Use structured output where applicable and explicitly disable thinking.
- Add durable per-Message generation claims and per-Conversation ordering.
- Persist and replay the AI Reply through the existing canonical WhatsApp flow.
- Record model, configuration, latency, input/output tokens, estimated cost, outcome, and safe error code without full Message bodies.
- Support only non-factual scenarios until V1.2 publishes approved Salon Knowledge.

**Observable behavior and acceptance criteria**

1. A safe non-factual inbound Message receives one short AI Reply; a retry replays the exact persisted reply.
2. Concurrent retries of one inbound Message create at most one normal LLM generation owner and one persisted AI Reply.
3. Only one generation is active for a Conversation. When a later Message arrives during an active previous generation, it is persisted first and the webhook performs a bounded wait. If still blocked, it returns a retryable non-2xx response with no customer-visible AI Reply. A provider retry or explicit local recovery preserves idempotency and may acquire processing only after the previous Message reaches a terminal result.
4. Distinct Conversations can generate in parallel.
5. A Message requiring unavailable RJ Studio facts receives clarification or Human Handoff, never an invented fact.
6. There is no automatic Claude-to-Terra fallback.
7. The 10-second deadline covers the entire webhook execution from inbound admission through the final HTTP response, including SQLite waits, Conversation ordering wait, provider backoff and retries, LLM calls, validation, the final transaction, and provider-response rendering. All stages use a monotonic `remaining_budget`; final persistence and rendering retain an explicit margin. A new LLM call cannot start without useful remaining time. The separate 30-second lease remains valid for coordination and restart recovery.
8. A local operation can list pending or stale Messages and recover the oldest eligible Message in a Conversation through a safe manual retry or Human Handoff. Recovery records a terminal result and preserves claim ownership, idempotency, and ordering.

**Main failure paths**

- Timeout, transient provider error, malformed structured output, or exhausted attempts follows safe clarification or Human Handoff policy. A transient retry uses only the time remaining in the same end-to-end deadline. If the persistence and response margin would be consumed, no further LLM attempt starts.
- A Message behind active Conversation processing follows this lifecycle: persist → bounded wait → retryable non-2xx with no customer-visible AI Reply if still blocked → provider retry or explicit local recovery → acquire processing only after the previous Message reaches a terminal result. Budget exhaustion while waiting for the predecessor follows this retryable ordering path.
- A provider can exhaust webhook retries after the Message was persisted. V1 therefore exposes pending and stale work to an explicit local recovery operation; it never assumes a stored Message will resume by itself. Fully autonomous recovery without an external stimulus requires a future executor and is intentionally deferred.
- Persistence or required configuration failure is an availability failure and must not acknowledge an unprepared reply.

**Test seams**

- FastAPI webhook behavior with a deterministic LLM test double.
- SQLite integration for claim ownership, replay, restart, lease expiry, Conversation ordering, and crash → exhausted provider retries → detectable pending Message → safe manual recovery.
- Narrow provider-contract tests for configuration and structured result translation.

**Explicit exclusions**

- Factual Salon Knowledge answers, persistent memory, full Intent catalog, style adaptation, scheduling, and external handoff notification.

### V1.2 — Approved Salon Knowledge

**Scope**

- Store Salon Knowledge in validated, versioned YAML.
- Support stable identifier, category/topic, draft or approved status, operational/commercial or technical type, approved_by, technical validated_by when needed, reviewed_at, and source/reference when available.
- Load only approved facts and select relevant knowledge progressively.
- Localize pilot facts: identity, location, channels, hours, supported Services and descriptions, prices or confirmation rules, relevant Professionals and specialties, fundamental policies, requires_human_consultation, and handoff conditions.

**Observable behavior and acceptance criteria**

1. A known approved fact may be used in an AI Reply with its stable reference in the structured decision.
2. A draft, absent, or irrelevant fact cannot be asserted as a salon fact.
3. A Customer claim about salon facts never overrides approved knowledge.
4. Technical facts needing validation remain unavailable until validated and approved.
5. Unknown price, policy, Service, Professional, or availability requests lead to clarification or Human Handoff.
6. Relevant knowledge fits the input budget without injecting the whole knowledge base for a narrow question.
7. Selecting Service knowledge also carries its applicable mandatory policies and `requires_human_consultation` rule into deterministic validation.

**Main failure paths**

- Invalid YAML or required metadata prevents that knowledge set from being used and gives the operator a safe failure.
- No relevant approved knowledge produces uncertainty or Human Handoff.

**Test seams and evals**

- Knowledge loading and selection tests cover approved/draft, validation, known, unknown, and conflicting-Customer-fact behavior.
- Grounding evals begin here with synthetic knowledge only.

**Explicit exclusions**

- CMS workflow, vector database, RAG service, unapproved facts, and broad knowledge outside the pilot.

### V1.3 — Bounded Conversation Context

**Scope**

- Build context from up to 12 prior Messages no older than 30 days.
- Limit Conversation history to approximately 2,000 tokens and total LLM input to approximately 4,000 tokens, removing oldest Messages first.
- Keep current inbound content and relevant approved knowledge ahead of old history.
- Do not create persistent summary or Customer memory.

**Observable behavior and acceptance criteria**

1. A recent reference is resolved when the required prior Message remains in budget.
2. Old or excess Messages do not enter model context after deterministic trimming.
3. A Customer returning within 30 days retains basic continuity when the budget permits it.
4. Missing or trimmed information triggers clarification, never assumption.
5. A later ordered Message sees state persisted by the earlier Message.

**Main failure paths**

- Budget pressure, malformed stored history, or missing context cannot expose unrelated history or create a false claim.

**Test seams and evals**

- Context-builder integration tests use synthetic stored Conversations.
- Context evals cover reference resolution, topic change, history truncation, and return after days.

**Explicit exclusions**

- Persistent summaries, Customer profile, preferences, Lead Stage, or V2 memory behavior.

### V1.4 — Intent and structured decision

**Scope**

- Produce one structured decision per inbound Message containing intents, reply_text, categorical uncertainty, Salon Knowledge references, structured critical factual claims, Human Handoff decision, and handoff reason.
- Support multiple Intents from this catalog: greeting, service_information, price, professional, hours, location, technical_guidance, appointment_interest, appointment_change, complaint, promotion_or_discount, human_request, and other.
- Do not request or persist chain-of-thought or free-text reasoning.

**Observable behavior and acceptance criteria**

1. Single-Intent and multi-Intent Messages produce applicable stable Intent values.
2. Availability questions may be understood as appointment-related without asserting actual availability.
3. The decision contains only allowed knowledge references and explicit uncertainty or handoff when facts are insufficient.
4. Invalid or incomplete structured output does not become an unvalidated AI Reply.
5. A critical factual claim remains an untrusted proposal until code matches its value and source against the selected approved knowledge or trusted integration result.

**Main failure paths**

- Schema-invalid output, unsupported Intent, or missing required field follows V1.1 safe failure policy.

**Test seams and evals**

- Provider-contract and FastAPI tests assert observable safe results.
- Intent evals cover single, multiple, appointment, complaint, and unknown combinations.

**Explicit exclusions**

- Separate generic classifier, hidden reasoning capture, Lead scoring, and next-best-action logic.

### V1.5 — Lívia persona

**Scope**

- Establish Lívia as a feminine, kind, attentive, technically safe, commercially competent AI Attendant for WhatsApp.
- Adapt formality, response size, emoji use, and vocabulary lightly to the Customer without changing identity or factual policy.
- Use up to three short paragraphs, a soft 450-character target, generally no more than one emoji, and an approximately 800-character hard ceiling when clarity requires it.

**Observable behavior and acceptance criteria**

1. Lívia may introduce herself naturally as “Oi! Sou a Lívia, do RJ Studio 😊”.
2. When asked whether she is AI, robot, or virtual, Lívia answers transparently.
3. Lívia never claims personal history, human identity, or invented experience.
4. Replies remain natural, non-corporate, non-repetitive, and free of excessive sales pressure while preserving safety rules.
5. Formal or terse Customers may receive more formal or shorter replies without persona drift.

**Main failure paths**

- A reply exceeding the hard ceiling, misrepresenting identity, repeating handoff confirmation, or conflicting with safety policy is rejected or follows safe failure policy.

**Test seams and evals**

- Deterministic persona rules are asserted at the structured decision and HTTP seams where possible.
- Persona evals cover formal, informal, terse, detailed, simple, and longer-answer Customers.

**Explicit exclusions**

- Invented personal stories, unrestricted style imitation, audio, voice, or multimodal interaction.

### V1.6 — Grounding, appointments and Human Handoff

**Scope**

- Enforce factual grounding and uncertainty across V1.
- Persist Human Handoff state and reason, send one short confirmation, suspend automation, and provide a local command to list and release handoffs. An inbound received while handoff is active receives the durable terminal processing result `suppressed` and no AI Reply.
- For appointment_interest, collect Service plus preferred day or period in up to two short clarification interactions. Professional preference is optional. Then create Human Handoff without promising availability.
- Send appointment changes, cancellations, and rescheduling directly to Human Handoff.
- Immediately hand off for explicit human request, relevant complaint, alleged damage, physical reaction, payment problem, serious conflict, legal threat, personalized technical risk, absent critical information, Service marked requires_human_consultation, or approved handoff condition.

**Observable behavior and acceptance criteria**

1. A factual response uses only approved Salon Knowledge, trusted integration output when available, or explicit Customer information relevant to the current Conversation.
2. Questions outside knowledge receive a concise limit, clarification, redirection, or Human Handoff.
3. A physical-symptom Message receives no diagnosis; it advises stopping an ongoing procedure, seeking appropriate professional evaluation, urgent medical care when signs may be urgent, then opens Human Handoff.
4. After handoff, later Messages remain persisted with terminal result `suppressed` and receive no customer-visible AI Reply. Their webhook requests receive only the provider acknowledgement required for delivery handling; that acknowledgement is not an outbound Message of the domain. A retry of the same inbound is acknowledged without generation or reply, including after restart and after a later manual release. Release affects only future inbound Messages. The initial confirmation is not repeated.
5. List and release operations are local, explicit, and do not expose full Message bodies in routine output.
6. Appointment interest preserves collected details and never claims confirmed availability or Appointment.

**Main failure paths**

- Missing handoff reason, failed state persistence, or inability to suspend automation is an availability failure and cannot falsely claim a person is taking over. When a decision activates Human Handoff, one transaction persists the inbound terminal result, optional one-time confirmation AI Reply, completed generation when one exists, Conversation handoff state and reason, and claim release as applicable; none of those effects may become visible independently.
- Completion and manual release races must validate both the current Conversation handoff state and the current claim owner token. A stale owner cannot finalize a reply or reactivate automation.
- An unavailable critical fact, technical policy, or Service rule opens Human Handoff rather than an unsupported reply.

**Test seams and evals**

- FastAPI and persistence tests cover handoff state, suppression, release, appointment collection, retry replay, failure before the atomic handoff commit, and a generation-finalize/manual-release race.
- A required regression test executes: handoff active → inbound B persisted as `suppressed` → acknowledgement lost → manual release → retry B → provider acknowledgement with no AI Reply or LLM call.
- Grounding, uncertainty, technical-risk, complaint, human-request, and appointment evals are required.

**Explicit exclusions**

- External notification delivery, calendar lookup, Appointment creation, rescheduling/cancellation execution, CRM workflow, and medical diagnosis.

### V1.7 — Eval and observability gate

**Scope**

- Create a seed suite of 28 synthetic or sanitized eval cases.
- Make eval execution and recorded runs part of V1 completion.
- Compare Claude Sonnet 5 and GPT-5.6 Terra with equivalent input, knowledge, prompt, token budget, and configuration.
- Provide concise metrics without full Message bodies, secrets, provider identifiers, or unnecessary PII.

**Observable behavior and acceptance criteria**

1. Each eval run records case count, run count, model/configuration, critical failures, grounding, Intent, handoff correctness, persona/naturalness, latency p50/p95, input/output tokens, and estimated cost.
2. Critical grounding and handoff cases have zero prohibited claims across recorded runs.
3. Every percentage names its numerator, denominator, and run count.
4. Important probabilistic cases run repeatedly. Naturalness and model comparisons receive paired, preferably blind, human review where applicable.
5. Sonnet remains primary unless Terra passes all critical gates, has no meaningful grounding or handoff regression, and is clearly better in quality or equivalently good with materially lower latency or cost. Approximately 25% is the initial operational threshold for cost/latency advantage.
6. The seed includes known/unknown prices, absent facts, unavailable availability, prompt injection, false Customer claims, technical risk, human-required Services, single/multiple Intent, context references, topic changes, return after days, persona variation, complaints, and Human Handoff.
7. Initial operational gates are p95 end-to-end latency no greater than 8 seconds and estimated cost no greater than US$10 per 1,000 completed AI Replies. The measured population includes every billable primary-model eval or smoke execution: successful calls, paid retries, and failed calls that consume tokens. Latency is reported per full execution, and cost includes every attempt while only completed AI Replies enter the response denominator. Exceeding either gate blocks V1.7 approval unless the threshold is explicitly revised with recorded evidence.

**Main failure paths**

- An eval fixture containing real Customer data, missing outcome metadata, or an unreported critical failure invalidates the run.
- Logging failure cannot expose full Message content or suppress customer-facing safety behavior.

**Test seams and evals**

- Deterministic tests verify metric redaction and run-record validity.
- The V1 eval suite complements, never replaces, HTTP, persistence, provider-contract, migration, and failure-path tests.

**Explicit exclusions**

- Automatic model switching, full observability platform, production alerting, and provider-independent production failover.

## Implementation decisions

- Preserve the existing WhatsAppProvider boundary. Twilio remains an HTTP adapter; Meta Cloud API is deferred.
- Add an LLM provider seam only because Claude production use and Terra eval use create genuine provider variation. Do not create a generic agent framework.
- Claude Sonnet 5 is the initial production model. GPT-5.6 Terra is an eval challenger only. There is no automatic provider fallback.
- Safe fallback means deterministic safe reply, clarification, or Human Handoff; it never means a second LLM provider.
- Use the canonical terms AI Attendant, AI Reply, Salon Knowledge, Operational/Commercial Fact, Technical Fact, Intent, and Human Handoff.
- Keep RJ Studio facts, tone, offers, policies, technical validation, and handoff conditions in localized knowledge or policy data, not generic Conversation orchestration.
- The knowledge source is validated YAML, not a CMS or vector store. The project owner approves publication. Joelma validates applicable chemistry, progressive, treatment, hair, color, eyebrow, and related facts. Rogério validates applicable mega hair facts. Both may validate a fact.
- Customer-provided information can assist the current Conversation but never becomes a new RJ Studio fact or V1 persistent memory.
- A durable generation record has processing, retryable, and completed states; owner token; 30-second lease; and at most two generation attempts. The LLM call is outside the SQLite write transaction. Only the valid owner can persist the result. The 10-second monotonic deadline starts at webhook/inbound admission and covers every wait and operation through rendering the HTTP response. Each stage receives only `remaining_budget`; final persistence and rendering keep a reserved margin. A transient retry can use only that remainder, and no LLM call starts without useful time. The lease is separate from this deadline.
- A completed AI Reply is replayed exactly. Active claims prevent concurrent generation; expired claims may be acquired after restart. The accepted crash window after provider response and before commit may cause a second provider charge but cannot create a second persisted AI Reply.
- One active generation per Conversation preserves Message order. A later Message is persisted, waits only within the webhook deadline, and otherwise receives retryable non-2xx handling without a customer-visible AI Reply. A later provider retry or explicit local recovery may process only the oldest eligible Message after its predecessor reaches a terminal result. The recovery operation lists pending/stale Messages and can safely retry or terminate them through Human Handoff. No stored Message is assumed to reactivate itself; autonomous recovery would require a future executor. V1 adds no queue, Redis, or worker.
- `suppressed` is a durable terminal processing result for an inbound received during active Human Handoff. It never owns a generation and never gains an AI Reply on retry, restart, or later release. Manual release changes the Conversation for future inbound Messages only.
- A handoff-producing finalization is one SQLite transaction: validate the current owner and Conversation state, persist the terminal inbound result and optional one-time confirmation AI Reply, mark an existing generation completed, activate Human Handoff with its reason, and release the claim as applicable. Manual release must validate current state and cannot make a stale generation owner valid.
- LLM output is an untrusted proposal. Knowledge references do not certify `reply_text`. Critical customer-visible facts—price, hours, Professional, Service, mandatory policy, and availability—must be represented in structured claims and validated in code against the selected approved Salon Knowledge or trusted integration result. Prefer deterministic composition of their canonical values; any conflicting or unsupported free-text value is corrected deterministically when safe or blocked before sending. Customer text cannot become trusted knowledge or policy.
- Deterministic handoff policy has precedence over the proposal. The LLM may request Human Handoff but cannot cancel one required by active handoff state, `requires_human_consultation`, a mandatory rule carried with selected Service knowledge/policy, or another approved deterministic condition.
- V1 runs one active application instance against persistent SQLite storage. Horizontal scaling, high availability, and distributed coordination are deferred.
- Raw Messages retain the existing 90-day explicit-purge policy. Logs exclude full Message bodies. LLM requests exclude phone numbers, provider identifiers, and unnecessary metadata, while Customer body text can itself contain PII.
- Standard Anthropic API retention is accepted for development and validation. V1 does not require ZDR or complex anonymization.

## Testing decisions

- The primary automated seam remains the FastAPI webhook interface because it observes adapter translation, application behavior, persistence, and rendered provider response together.
- SQLite integration tests are required for durable claim ownership, Conversation ordering, migration, restart, lease expiry, replay, handoff, and retention behavior.
- A deterministic LLM test double supports normal automated tests. Tests assert observable responses, persisted state, and provider-call counts, not private helper calls or prompt implementation.
- Critical deterministic coverage includes valid reply, replay, concurrent retry, concurrent Conversation ordering including persist → bounded wait → retryable response → later retry/local recovery, crash with exhausted provider retries and detectable pending recovery, accumulated SQLite/ordering waits consuming the webhook deadline before an LLM call, retryable failure, exhausted failure, stale owner completion, restart, invalid structured output, unapproved knowledge, correct knowledge reference with a conflicting textual price, mandatory `requires_human_consultation` despite an LLM `handoff=false` proposal, atomic handoff rollback, finalize/release race, suppression surviving acknowledgement loss/restart/release, and log redaction.
- Migration tests preserve V0.1 Messages and map existing reply relationships consistently with the V1 generation model.
- Evals use synthetic or explicitly sanitized content. The 28-case seed is a starting denominator, not general statistical proof.
- Critical factual grounding and Human Handoff evals require zero prohibited claims. Other reports name case count and run count.
- The project owner reviews naturalness, commercial posture, clarity, overall experience, and Lívia persona. Joelma reviews applicable technical cases. Rogério reviews applicable mega hair cases.
- Real provider smoke and eval runs use configured credentials only after the relevant slice is implemented. Repository artifacts never contain secrets or real Customer content.

## Definition of done

### V1 code complete

V1 is code complete only when all seven slices meet their acceptance criteria, deterministic critical tests pass, the 28-case eval seed has recorded runs, critical evals have zero prohibited claims, metrics include denominators, the p95/cost operational gates pass or are explicitly revised with evidence, and Sonnet/Terra comparison evidence is recorded.

### Ready for autonomous real-customer operation

Code completion does not authorize regular autonomous operation with real Customers. Before that operation, confirm:

- approved real Salon Knowledge for the pilot;
- reliable external Human Handoff notification for a responsible person;
- current provider retention, data use, commercial terms/DPA, PII minimization, applicable salon privacy policy, LGPD requirements, and practical value of ZDR;
- one active instance with persistent storage;
- smoke and eval results using real configuration without committing secrets or real Customer content.

## Out of scope

- CRM, persistent Customer memory, Lead Stage, Lead scoring, and Next Best Action
- Follow-up, cross-sell/upsell engine, and discount policy
- Trinks or real calendar, availability, Appointment creation, rescheduling, or cancellation integration
- Audio, images, photos, hair analysis, and multimodal behavior
- Google Ads, GCLID/UTM, attribution, conversion, and growth analytics
- SaaS, tenant infrastructure, tenant_id, generic onboarding, and multi-business configuration
- Horizontal scaling, high availability, Redis, queues, workers, distributed locks, and generic integration frameworks without demonstrated need
- Meta Cloud API implementation, automatic LLM provider switching, and a customer-facing administration interface
- External Human Handoff notification delivery; it is a production gate, not a V1 implementation commitment
- Automated pending-Message recovery executor, generic fact-checking service, or second reviewing LLM

## Further notes

- V1.1 intentionally proves costly generation safety before factual salon answers are enabled.
- Outside active Human Handoff, an inbound Message may produce at most one customer-visible AI Reply. Retries never create additional AI Replies. During active Human Handoff, later inbound Messages are persisted and receive only the provider HTTP acknowledgement, which is not an outbound Message of the domain. Multiple WhatsApp bubbles are deferred.
- Missing pilot knowledge is supported: Lívia clarifies or hands off rather than treating it as an implementation failure.
- ADR 0005 records durable generation claims. ADRs 0001, 0003, and 0004 continue to govern provider independence, inbound/reply durability, and raw Message retention.
